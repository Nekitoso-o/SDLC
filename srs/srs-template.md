## 1. Введение {#1-introduction}

Настоящий документ представляет собой спецификацию требований к программному обеспечению (SRS) для кроссплатформенного десктопного приложения **Game Shelf** (версия 0.2). Продукт предназначен для локальной каталогизации личной коллекции видеоигр с различных игровых платформ, отслеживания статуса их прохождения и автоматического выявления неактивных («забытых») позиций бэклога. Документ определяет функциональные и качественные границы системы и организован в соответствии со стандартом ISO/IEC/IEEE 29148 для последующего проектирования, разработки и верификации.

### 1.1 Назначение документа {#11-document-purpose}

Настоящий SRS определяет **ЧТО** система Game Shelf должна делать на уровне внешних интерфейсов и показателей качества, не навязывая низкоуровневых деталей реализации. Документ служит единой технической основой для согласования требований между разработчиком, Заказчиком (напарником по команде) и преподавателем на всех этапах жизненного цикла разработки ПО. На базе данного документа выполняются проектирование архитектуры (SDD) и формирование сценариев приёмочного тестирования.

### 1.2 Область применения продукта {#12-product-scope}

Приложение **Game Shelf** (релиз 1.0) — это автономный персональный органайзер видеоигр, решающий проблему фрагментации игровых библиотек между различными платформами (PC, PlayStation 5, Nintendo Switch, Xbox) и накопления большого количества приобретённых, но не пройденных игр («бэклога»). Внедрение системы позволяет пользователю поддерживать порядок в коллекции и своевременно возвращаться к отложенным проектам.

**В область применения продукта входит:**

* Локальное хранение и табличное отображение карточек видеоигр с указанием обложки, названия (`Title`), платформы (`Platform`), статуса прохождения (`Status`), даты добавления (`Date Added`) и состояния активности (`Activity`).
* Мгновенный текстовый поиск по названию (`Search...`) и фильтрация коллекции по статусам (`All Games`, `Backlog`, `Playing`, `Completed`, `Paused`, `Wishlist`).
* Автоматический расчёт длительности простоя игры с даты добавления или последнего обращения и визуальная подсветка «забытых» игр в таблице (`! Idle 90d+`, `! Never played`), а также быстрый отбор через фильтр `! Inactive (30d+)`.
* Добавление новых записей (`+ Add Game`), пакетное обновление статуса (`Update selected`), редактирование (`Edit`) и удаление (`Delete`) карточек из локальной базы.

**В область применения НЕ входит:**

* Покупка, скачивание, установка или запуск исполняемых файлов видеоигр.
* Интеграция с платёжными системами цифровых магазинов (Steam, Epic Games Store, PS Store).
* Облачная синхронизация аккаунтов между устройствами и многопользовательские социальные функции (чаты, ленты друзей).

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

**Game Shelf** разрабатывается как новый полностью самостоятельный программный продукт (offline-first), не входящий в состав коммерческих игровых лаунчеров. Приложение функционирует локально на рабочем месте пользователя, храня метаданные игр и кэш обложек в локальной файловой системе без необходимости постоянного подключения к Интернету. Продукт ориентирован на пользователей, которым необходим единый лёгкий инструмент учёта коллекции поверх разрозненных цифровых библиотек.

### 2.2 Функции продукта {#22-product-functions}

На верхнем уровне система предоставляет следующие основные возможности:

* **Добавление карточки игры (`+ Add Game`):** ввод названия, выбор одной или нескольких платформ, установка начального статуса и фиксация даты добавления.
* **Текстовый поиск (`Search...`):** фильтрация списка игр в реальном времени по вхождению подстроки в поле `Title`.
* **Навигационная фильтрация по статусам:** переключение между выборками `All Games`, `Backlog`, `Playing` и `Completed` через боковую панель.
* **Табличный просмотр коллекции:** отображение игр с миниатюрой обложки, названием, платформой, статусом, датой добавления и меткой активности.
* **Визуальная индикация неактивных игр:** автоматическая подсветка строк с «забытыми» играми (`! Idle 90d+`, `! Never played`) и фильтрация по кнопке `! Inactive (30d+)`.
* **Пакетное и индивидуальное управление:** массовое изменение статуса отмеченных записей (`Update selected`), редактирование (`Edit`) и удаление (`Delete`).

### 2.3 Ограничения продукта {#23-product-constraints}

* **Кроссплатформенность:** Приложение должно функционировать и сохранять единообразную компоновку интерфейса в настольных ОС Windows (10/11), Linux (Ubuntu 22.04+, Fedora) и macOS (12+).
* **Технологический стек:** Разработка должна вестись на языке Java (версии 21 LTS и выше) с использованием кроссплатформенного графического фреймворка JavaFX и локальной СУБД SQLite.
* **Автономность и права доступа:** Приложение должно работать исключительно в пользовательском пространстве ОС без запроса привилегий администратора (`root`).
* **Ограничение объёма кэша:** Размер локальной базы данных и кэша миниатюр обложек игр не должен превышать 500 МБ.

### 2.4 Характеристики пользователей {#24-user-characteristics}

Основным классом пользователей системы является **Геймер / Коллекционер видеоигр**:

* **Профиль поведения:** владеет библиотекой от нескольких десятков до нескольких тысяч игр на одной или нескольких платформах (PC, Switch, PS5); регулярно пополняет коллекцию и сталкивается с проблемой отложенного прохождения.
* **Уровень подготовки:** средний и высокий уровень владения ПК; специальные навыки администрирования не требуются.
* **Частота использования:** 2–5 раз в неделю для обновления прогресса, добавления новинок и выбора следующей игры из бэклога.
* **Требования к UX:** высокая читаемость статусов и контрастное выделение неактивных позиций без перегруженности интерфейса.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

* **Допущение о системном времени ОС:** Корректность вычисления количества дней простоя (`Idle 30d+` / `90d+`) зависит от точности системных часов и часового пояса на компьютере пользователя. При некорректной системной дате индикаторы простоя могут отображаться неточно.
* **Зависимость от локальной файловой системы:** Приложение зависит от наличия прав на чтение и запись в пользовательский каталог хранения данных (минимум 500 МБ свободного места).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

Графический интерфейс представляет собой однооконное десктопное приложение на базе фреймворка JavaFX. Визуальный каркасный макет интерфейса приведён в Приложении А.

**Структурная спецификация интерфейса на языке SysMLv2:**

```sysml
package GameShelfUI {
    public part def MainWindow {
        part filterSearchBar : FilterSearchBar;
        part gameCatalogGrid : GameCatalogGrid;
        part gameActionPanel : GameActionPanel;
    }

    part def FilterSearchBar {
        attribute searchInput : String;
        part addGameButton : Button [1] { attribute label = "+ Add Game"; }
        part categoryFilters : FilterItem [4]; // All Games, Backlog, Playing, Completed
        part inactiveFilterButton : Button [1] { attribute label = "! Inactive (30d+)"; }
    }

    part def GameCatalogGrid {
        part rows : GameCatalogRow [*];
    }

    part def GameCatalogRow {
        attribute rowNumber : Integer;
        attribute coverImage : String;
        attribute gameTitle : String;
        attribute platform : String;
        attribute status : String; // "Playing" | "Backlog" | "Paused" | "Wishlist" | "Completed"
        attribute dateAdded : String;
        attribute activityBadge : String; // "Active" | "! Idle 90d+" | "! Never played"
        attribute isHighlightedInactive : Boolean;
    }

    part def GameActionPanel {
        part updateSelectedButton : Button [1] { attribute label = "Update selected"; }
        part editButton : Button [1] { attribute label = "Edit"; }
        part deleteButton : Button [1] { attribute label = "Delete"; }
    }
}
```

**Описание элементов управления и поведения интерфейса:**

* **Верхняя панель и боковое меню (`FilterSearchBar`):** В верхней части окна расположены заголовок `Game Shelf`, поле поиска `Search...` и кнопка `+ Add Game`. Левая боковая панель содержит фильтры по статусу прохождения (`All Games`, `Backlog`, `Playing`, `Completed`), отделённые разделительной линией от кнопки фильтрации неактивных записей `! Inactive (30d+)`.
* **Таблица каталога (`GameCatalogGrid`):** Центральная область содержит нумерованный список карточек с колонками миниатюры обложки, `Title`, `Platform`, `Status`, `Date Added` и `Activity`. Строки с «забытыми» играми выделяются контрастной фоновой заливкой, пунктирной рамкой и предупреждающим бейджем (`! Idle 90d+`, `! Never played`). При пустом результате поиска отображается информационное сообщение «Игры не найдены».
* **Нижняя панель действий (`GameActionPanel`):** Содержит кнопку пакетного обновления статуса `Update selected` слева, а также кнопки `Edit` и `Delete` справа.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Специализированные внешние аппаратные интерфейсы не используются. Приложение взаимодействует со стандартными устройствами ввода (клавиатура, мышь/трекпад), дисплеем и локальными накопителями данных (HDD/SSD) средствами операционной системы и виртуальной машины Java (JVM).

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

* **Файловый API операционной системы (Windows / Linux / macOS):** Чтение и запись файла базы данных, сохранение локальных изображений обложек и получение текущей системной даты через пакет `java.time` для расчёта длительности простоя.
* **Встраиваемая СУБД SQLite (версия >= 3.40):** Взаимодействие через драйвер `sqlite-jdbc` (стандартный интерфейс Java JDBC) для выполнения локальных SQL-запросов выборки, вставки, обновления и удаления карточек игр.

### 3.2 Функциональные требования {#32-functional}

* **ID:** REQ-FUNC-001-01
* **Title:** Добавление новой карточки игры в каталог
* **Statement:** При нажатии кнопки «+ Add Game» система должна предоставлять форму создания записи и сохранять новую карточку игры с обязательными полями `Title`, `Platform`, `Status` и `Date Added`.
* **Rationale:** Позволяет пользователю пополнять единую библиотеку играми с любых платформ.
* **Acceptance Criteria:** После заполнения обязательных полей и подтверждения новая игра немедленно отображается в таблице `GameCatalogGrid` и сохраняется в локальной БД.
* **Verification Method:** Demonstration
* **More Information:** Связано с компонентом `FilterSearchBar` (подраздел 3.1.1).

* **ID:** REQ-FUNC-002-01
* **Title:** Табличное отображение личной коллекции
* **Statement:** Система должна отображать сохранённые карточки игр в виде таблицы `GameCatalogGrid`, содержащей колонки порядкового номера, миниатюры обложки, `Title`, `Platform`, `Status`, `Date Added` и `Activity`.
* **Rationale:** Обеспечивает структурированный обзор всей игровой библиотеки в одном окне.
* **Acceptance Criteria:** Все записи из локальной базы данных корректно отрисовываются в таблице с заполнением всех 7 колонок без обрезания ключевых метаданных.
* **Verification Method:** Demonstration
* **More Information:** Соответствует макету в Приложении А.

* **ID:** REQ-FUNC-003-01
* **Title:** Текстовый поиск и категориальная фильтрация
* **Statement:** Система должна фильтровать отображаемый список игр в реальном времени при вводе текста в поле «Search...» (регистронезависимый поиск по подстроке в `Title`) и при выборе категории в боковом меню (`All Games`, `Backlog`, `Playing`, `Completed`).
* **Rationale:** Обеспечивает быструю навигацию в больших коллекциях.
* **Acceptance Criteria:** При вводе поискового запроса или клике по категории в таблице остаются только записи, удовлетворяющие обоим активным условиям фильтрации.
* **Verification Method:** Test
* **More Information:** См. подраздел 3.3.1 по времени отклика.

* **ID:** REQ-FUNC-004-01
* **Title:** Автоматическое определение неактивных («забытых») игр
* **Statement:** Система должна вычислять интервал времени с даты добавления (`Date Added`) или последнего запуска для игр со статусом `Backlog` или `Paused` и присваивать им статус неактивности при простое свыше 30 календарных дней (`! Idle <N>d+`) либо при полном отсутствии запусков (`! Never played`).
* **Rationale:** Помогает пользователю выявлять отложенные игры, о которых он забыл (реализовано по запросу Заказчика в PR).
* **Acceptance Criteria:** Игры со статусом `Playing` или `Completed` имеют метку `Active`; игры со статусом `Wishlist` имеют метку `-`; игры со статусом `Backlog`/`Paused` старше 30 дней получают соответствующий предупреждающий бейдж.
* **Verification Method:** Test
* **More Information:** Адресует бизнес-цель борьбы с неразобранным бэклогом (раздел 1.2).

* **ID:** REQ-FUNC-005-01
* **Title:** Визуальная подсветка и фильтрация неактивного бэклога
* **Statement:** Система должна визуально выделять в таблице `GameCatalogGrid` строки с неактивными играми контрастной фоновой заливкой и пунктирной обводкой, а при нажатии кнопки «! Inactive (30d+)» отображать исключительно такие записи.
* **Rationale:** Привлекает визуальное внимание пользователя к «забытым» позициям коллекции.
* **Acceptance Criteria:** На главном экране строки с метками `! Idle 90d+` и `! Never played` визуально отличаются от активных строк; активация фильтра `! Inactive (30d+)` скрывает все активные игры.
* **Verification Method:** Demonstration
* **More Information:** Отражено на UI-мокапе в Приложении А.

* **ID:** REQ-FUNC-006-01
* **Title:** Обновление статуса, редактирование и удаление записей
* **Statement:** Система должна обеспечивать пакетное изменение статуса для выделенных в таблице игр по кнопке «Update selected», редактирование атрибутов выбранной карточки по кнопке «Edit» и удаление записи из локальной базы по кнопке «Delete».
* **Rationale:** Позволяет поддерживать актуальность статусов коллекции по мере прохождения игр.
* **Acceptance Criteria:** Изменение статуса через `Update selected` или `Edit` обновляет строку в таблице и сбрасывает индикатор неактивности при переводе игры в статус `Playing`; нажатие `Delete` удаляет запись из БД.
* **Verification Method:** Test
* **More Information:** Диалоговое окно подтверждения удаления отложено до этапа SDD (раздел 2.6).

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

* **REQ-PERF-001-01:** Время выполнения текстового поиска (`Search...`) и переключения фильтров по локальному каталогу объёмом до 5 000 записей не должно превышать 100 мс.
* **REQ-PERF-002-01:** Холодный запуск приложения, загрузка каталога из SQLite и пересчёт индикаторов активности (`Activity`) для 5 000 записей должны занимать не более 2 секунд.

#### 3.3.2 Безопасность {#332-security}

* **REQ-SEC-001-01:** Все данные коллекции и пользовательские оценки должны храниться исключительно в локальной директории профиля пользователя; приложение не должно передавать данные или телеметрию на внешние серверы.

#### 3.3.3 Надёжность {#333-reliability}

* **REQ-REL-001-01:** Все операции изменения и удаления записей в локальной базе данных SQLite должны выполняться в рамках атомарных транзакций JDBC, предотвращая повреждение файла БД при аварийном завершении работы.
* **REQ-REL-002-01:** При отсутствии или повреждении файла миниатюры обложки система должна подставлять стандартную векторную заглушку без генерации необработанного исключения.

#### 3.3.4 Доступность {#334-availability}

* **REQ-AVAIL-001-01:** Приложение должно обеспечивать 100% заявленной функциональности в полностью автономном режиме (offline) без подключения к сети Интернет.

#### 3.3.5 Наблюдаемость {#335-observability}

* **REQ-OBS-001-01:** Исключения при работе с файловой системой, ошибки чтения БД и предупреждения о достижении лимита кэша обложек (500 МБ) должны записываться в локальный журнал `gameshelf.log`.

### 3.4 Соответствие стандартам {#34-compliance}

1. **СТП 01–2024 БГУИР** — соблюдение правил оформления, структуры, нумерации рисунков и ведения технической документации по проекту (раздел 1.4).
2. **ISO/IEC/IEEE 29148** — соблюдение требований к однозначности, проверяемости и трассируемости формулировок в спецификации требований к ПО.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

Приложение поставляется в виде автономного портативного архива (Portable) для каждой целевой ОС. Запуск выполняется распаковкой архива без необходимости предварительной установки системных служб или глобальной JRE.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

Сборка и управление зависимостями выполняются с помощью системы сборки Apache Maven; формирование автономного дистрибутива со встроенной средой выполнения JRE осуществляется инструментом `jlink` / `jpackage`.

#### 3.5.3 Распределение {#353-distribution}

Однопользовательское локальное развёртывание на персональном компьютере. База данных `gameshelf.db` и папка кэша обложек `covers/` размещаются в каталоге данных приложения текущего пользователя.

#### 3.5.4 Сопровождаемость {#354-maintainability}

Архитектура приложения строится по паттерну MVVM / MVC (с использованием FXML-разметки и контроллеров JavaFX) с чёткой изоляцией бизнес-логики расчёта неактивности и слоя доступа к БД (DAO/Repository) от пользовательского интерфейса.

#### 3.5.5 Повторное использование {#355-reusability}

Модуль управления каталогом и вычисления метрик простоя бэклога оформляется в виде независимого Maven-модуля и JAR-библиотеки (`gameshelf-core.jar`).

#### 3.5.6 Переносимость {#356-portability}

Обеспечивается поддержка операционных систем Windows (10/11, x64), macOS (12+, x64/ARM64) и Linux (Ubuntu 22.04+, Fedora, Arch Linux) за счёт кроссплатформенной виртуальной машины JVM (Java 21+), фреймворка JavaFX и API `java.nio.file.Path`.

#### 3.5.7 Стоимость {#357-cost}

Проект разрабатывается с открытым исходным кодом; использование платных библиотек, лицензий и коммерческих облачных API не предусмотрено.

#### 3.5.8 Сроки {#358-deadline}

Согласование спецификации SRS и графических прототипов завершается в 5-м семестре (октябрь 2026 г.); программная реализация планируется на 6-й семестр (2027 г.).

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

На этапе прототипирования подтверждается корректность компоновки главного окна и визуальной индикации неактивных игр на интерактивном UI-мокапе в Excalidraw.

#### 3.5.10 Управление изменениями {#3510-change-management}

Все изменения в спецификации и графических артефактах ведутся в изолированной ветке Git (`feature/gameshelf-srs`) с фиксацией коммитов по стандарту Conventional Commits и обязательным код-ревью через Pull Request перед слиянием в `main`.

### 3.6 ИИ/МО {#36-aiml}

Использование моделей машинного обучения и алгоритмов искусственного интеллекта в текущей версии приложения Game Shelf не предусмотрено.
